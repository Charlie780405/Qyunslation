# PLAN-081：双路翻译准入与排队提醒、服务 API、QyunsGen 接入及模型对照

> 状态：**规划中；只完成只读核查，未改运行配置、未部署、未触发生产任务**。
> 日期：2026-10-20
> 依赖：PLAN-053（`/api/v1` 对外入口）、PLAN-067/077（工作台任务与身份边界）、PLAN-071（质量流水线）、PLAN-072（任务持久化与恢复）、PLAN-078（任务状态/前端体验）、PLAN-079（QA 处置边界）。
> Skill：`planning-and-task-breakdown`、`api-and-interface-design`。

## 1. 目标

把 Qyunslation 建成可被 QyunsGen 等系统调用的受控文档翻译服务。全站最多同时执行 **2 个文档翻译任务**；超过后接受请求并持久排队，页面明确显示“当前繁忙、排队位置”，任务空出后自动启动并在本站通知提交方。提供稳定、可追踪、幂等、鉴权的异步 API；调用方可上传文件、查状态/进度、取得翻译结果。QyunsGen 先把译文作为待确认草稿呈现，不自动写入临床方案或 EDC 的受监管业务字段。

这里的“2 路”指**全站同时执行的文档任务数**，不等于 2 个用户、2 个模型推理请求，也不等于每个任务内部的分段并发。模型请求并发必须单独受控并通过压力验证；页面容量与模型服务的实测能力都通过后，才可宣称“端到端两路并行已就绪”。

## 2. 当前基线与证据

### 2.1 应用任务与容量

- 只读健康探测：`GET /api/v1/health` 返回 `schema=034h`、`db=ok`。
- 2026-10-20 本次查询 `translation_run_record` 中 `queued/scanning/translating/rendering` 数为 **0**；按用户设定的 2 个任务上限，当前候选空位为 **2/2**。但这只是容量计算：当前 `POST /translation-runs` 在落库后直接调用 `_launch_translation_run`，还没有跨请求/跨进程的全局 2 路准入锁，因此当前代码尚不能保证上限。
- 旧表 `workbench_translation_run` 仍有 2 条 `translating`，最后更新于 **2026-09-15**；这两条不计入新任务空位，但需通过心跳、外部执行器和持久化产物核验后，将陈旧状态恢复为准确终态，不能只因日期久就直接删除。
- 本次宿主快照：负载均值约 `1.41/1.63/1.70`、可用 RAM 约 `15 GiB`、根卷可用约 `83 GiB`（已用 82%）。这些指标来自共享宿主，只能说明此刻尚有余量，不足以证明 2 个大型 PDF/Office 任务的峰值安全。
- 上次运行时观测到 Qwen Ollama `OLLAMA_NUM_PARALLEL=1`，且两个任务/每任务分段并发 4 的配置会将多段请求叠加到一个模型服务。2026-10-20 本次对模型端的直连探测超时；**本次无法确认它现在是否在线或是否支持 2 路推理**。启动前须重新核对模型主机健康、GPU 显存、Ollama 并行参数和真实双任务压测。

### 2.2 上传边界

- 应用默认单文件上限是 **256 MiB**（`DEFAULT_MAX_UPLOAD_BYTES`；环境变量 `QYUNSLATION_MAX_UPLOAD_BYTES` 可覆盖）；分片上传接口单片最多 **8 MiB**。
- 256 MiB 是当前输入硬边界，不代表所有 256 MiB 文档都能在同一时限内成功翻译。扫描页数、PDF 结构、表格/图片比例、解压膨胀、输出文件大小都会改变资源占用。
- 建议首发维持 **256 MiB 硬上限**，把值显式同步到应用入口和反向代理，先按格式/页数/文本量压力测出软提示阈值和耗时区间，不在没有证据时把硬上限调大或承诺某个页数上限。

### 2.3 模型与 GS101 比较基线

- 仓库模型 profile 已将 `internal-qwen-quality` 指向本地 Ollama `qwen3.6:35b-a3b`；`internal`/`confidential` 全文只允许本地 Qwen，`public` 才允许 DeepSeek 全文翻译。这一数据外发门禁必须保留。
- 上一轮按相同提示词、分段和参数，对 `docs/Resources/GS101注射液临床开发计划-V1.0-20251023-Final-Clean.docx` 的 13 个文本块做了模型文本对照（约 207 KB，549 个文本段落）。观察结果：Qwen 模型请求总耗时约 **77.2 秒**，DeepSeek API（`deepseek-chat` 实际返回 `deepseek-flash`）约 **14.7 秒**；段落标记覆盖 Qwen **546/549**、DeepSeek **549/549**；546 个可比段落归一化文本相似度均值约 **92.1%**，逐段完全一致约 **59.3%**；数字存在性检查 Qwen **94.4%**、DeepSeek **97.9%**。
- 这些数字描述的是**单样本文本差异与接口耗时**，相似度高不等于医学正确，差异也不等于错误；该轮没有做人工盲审、临床 MQM 评分、最终 DOCX 版式/表格复核或并行性能验证。发布前必须补这些门禁，不能仅据此把 DeepSeek 设为临床默认模型。

## 3. 决策

1. **准入单位是文档任务**：默认全局最多 2 个处于执行阶段的 run；同一租户及不同入口合并计数，取消/失败/完成/QA 等待均释放执行槽位。
2. **队列持久化于数据库**：请求创建即获得 `run_id` 并进入 `queued`；由单一原子认领机制按 FIFO（同优先级）调度，不由浏览器刷新/重试触发执行。调度器必须支持多 API worker 竞争、进程重启、心跳过期与取消。
3. **模型并发独立限流**：单任务分段并发不得乘以活动文档数后无界送模。先以 Qwen 当前实际服务配置压测，分别测 1/2 个文档任务和聚合推理请求；在 VRAM、失败率、P95 完成时间符合验收前，不把 Ollama `NUM_PARALLEL=2` 当作已达成事实。
4. **始终显示容量，空位自动提醒**：页面固定显示 `执行中 x/2 · 排队 y`；满载时显示排队位置和可撤销状态。空位释放后队列任务自动启动，页面/站内通知告知“已开始”，不要求重新点击。首发不依赖邮件或浏览器通知权限。
5. **复用现有异步资源/API**：保留上传会话、预检、参数确认、`translation-runs`、事件/状态、产物下载合同；为服务端调用补机器身份、租户/项目映射和最小权限，不让 QyunsGen 直连 Ollama/DeepSeek，也不把模型密钥放到浏览器。
6. **翻译结果先是草稿**：QyunsGen 显示源文件、目标语言、Qyunslation run 链接、状态和译文产物；涉及方案、知情同意、EDC 配置、受试者/安全性数据的内容需业务人员确认后才可回填。保留源文件哈希、模型/术语版本、语言方向、产物和人工修改来源。
7. **i18n 与机器翻译分工清晰**：QyunsGen PLAN-516 的 `preferredLocale`、`supportedLocales`、`NEXT_LOCALE`、UI 词典和 `LocalizedText` 解决页面/字段多语言展示与存储上下文；它们不是翻译模型或自动翻译 API。可用于传递请求语言、显示状态/错误、呈现已有本地化内容，但译文生成仍由 Qyunslation 完成。

## 4. API 草案（先兼容现有 `/api/v1`）

现有机器可复用链路：

1. `POST /api/v1/upload-sessions` 创建上传会话；`PATCH /api/v1/upload-sessions/{id}` 按 `Content-Range` 分片；`POST /api/v1/upload-sessions/{id}/complete` 得到预检记录。现有单片上限 8 MiB、默认全文件 256 MiB。
2. `POST /api/v1/translation-runs/validate` 返回可执行配置/数据级别/模型 egress 和 `config_digest`；调用方再 `POST /api/v1/translation-runs`，带 `Idempotency-Key` 创建异步 run。
3. `GET /api/v1/translation-runs/{id}` 取状态；`GET .../{id}/events?after_sequence=` 取增量事件；`GET .../{id}/artifacts` 和 artifact 下载接口取结果。

计划在实现阶段先冻结以下机器接口合同，不另建第二套翻译执行逻辑：

```text
POST /api/v1/upload-sessions
PATCH /api/v1/upload-sessions/{uploadId}       Content-Range: bytes ...
POST /api/v1/upload-sessions/{uploadId}/complete
POST /api/v1/translation-runs/validate
POST /api/v1/translation-runs                  Idempotency-Key: <caller key>
GET  /api/v1/translation-runs/{runId}
GET  /api/v1/translation-runs/{runId}/events?after_sequence=N
GET  /api/v1/translation-runs/{runId}/artifacts
GET  /api/v1/translation-runs/{runId}/artifacts/{artifactId}
GET  /api/v1/capacity                            执行上限、执行数、排队数、是否可立即运行
```

`/capacity` 是计划新增的只读能力端点；返回对象至少包含 `maxActiveRuns`、`activeRuns`、`queuedRuns`、`availableSlots`、`estimatedWait`（无可靠估算时为 `null`），不暴露其他租户文件名或任务 ID。排队必须由 `run.status=queued` 和状态事件体现，不用非标准 `429` 迫使调用方自行重试。

服务身份不能直接复用浏览器 CSRF 流程。实现前确认 QyunsApps/Authentik 可签发和验证的机器身份合同；令牌绑定 `audience`、调用服务、tenant/project 与 `translation:submit/read/cancel` scopes，敏感操作仍由本地授权检查。若短期不能加入 machine principal，则 API 先限于受控内网适配器，不对公众开放静态 API key。

所有错误使用稳定的机器码与一致 JSON 形状；上传、创建任务、状态查询及下载均按服务 principal 的租户边界授权。幂等键重复提交返回同一 run；同一键参数不同返回 `409 IDEMPOTENCY_CONFIG_MISMATCH`。首期使用有退避上限的轮询读取状态；将签名 webhook 留作可选扩展，避免首发同时引入回调重放/SSRF 风险。

## 5. 工作包与验收

### 081a：冻结真实容量和旧任务状态

**内容：** 记录 API/Ollama 可用性、CPU/RAM/磁盘/GPU、模型并行参数、每任务 chunk 并发、上传/代理边界和活跃任务数；复核两条旧 `workbench_translation_run` 是否真陈旧。只修复有执行器/心跳/产物证据支持的状态，不删历史产物。

**验收：**
- [ ] 形成时间戳明确的运行基线，区分 2 个文档槽位、Ollama 推理并行度和分段请求并发。
- [ ] 所有 active 状态可关联活动 executor 或按恢复合同终结；旧记录没有仅凭“时间久”清除。
- [ ] 确认应用和边缘上传上限一致，说明 256 MiB 实际有效与否。

**验证：** 只读状态查询、运行时配置审计、模型端健康/GPU 采样；陈旧任务通过 heartbeat 和外部 task state 对账。**依赖：** 无。**估算：** 0.5–1 人日。

### 081b：两路全局准入、持久队列与模型信号量

**内容：** 创建任务时原子申请执行槽位；满载则只入队不直接 `_launch_translation_run`。槽位由终态释放，调度器自动 FIFO 认领；进程崩溃、取消、重复请求、超时和 heartbeat 失效均需恢复。增加独立的模型请求限流，并避免每 run 的 `concurrent=4` 在双任务时乘成 8 个无界请求。

**验收：**
- [ ] 多 worker 并发压入任务时，`scanning/translating/rendering` 总数始终不超过 2，且不重复启动；超出任务保留 `queued`。
- [ ] 终态、取消、worker 恢复后正确释放/回收槽位，排队任务无需浏览器参与即可自动启动。
- [ ] Qwen 的请求并发值来自 1/2 路压力数据；GPU OOM、错误率和 P95 任务时长达到预先记录的门槛后，才开启 2 个模型推理请求。

**验证：** 并发竞争、重启恢复、租户混合、取消释放、模型超时和 1/2 路双任务压测。**依赖：** 081a。**估算：** 2–3 人日。

**验收：**
- [ ] 始终能看到执行上限 2、当前执行数、排队数和当前 run 状态；满载时明确说明将等待且不需重新提交。
- [ ] 空位释放并自动启动后，在当前页面及重新打开的任务列表中均看到提醒/执行状态。
- [ ] 页面不显示其他租户的文件名、run ID 或用户信息；匿名/无权限用户无法读取容量明细。

**验证：** 两路满载/第三任务排队、空位自动启动、刷新/断线重连、取消、浏览器多标签及租户隔离走查。**依赖：** 081b。**估算：** 1–2 人日。

**内容：** 形成 OpenAPI/合同文档、服务身份、tenant/project 授权、幂等语义、上传、参数校验、run 状态、增量事件、产物下载、容量端点、速率/配额和统一错误结构。优先复用现有接口；机器认证与浏览器 Cookie/CSRF 身份路径分开。

**验证：** PLAN-051/063 的 MQM 和术语质控流程、DOCX 结构差异、GPU/磁盘/CPU 峰值，1/2 文档并发回归。**依赖：** 081a；DeepSeek 试验另须通过资料分级/外发门。**估算：** 1–2 人日，不含人工临床审阅时间。

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| `queued` 当前创建后立即启动，且多个 API worker 能同时提交 | 超过两路、GPU/磁盘竞争、状态与用户提示不一致 | 数据库原子认领/租约，任何入口均走同一调度器；上线前做竞争压测 |
| Ollama 实际仍是单并行或模型服务不可达 | 两个任务都占槽但模型排队；完成时间增加 | 分开显示任务槽/模型请求槽；实测后再开两路推理；健康失败及时阻止新任务或保留排队 |
| 256 MiB 文件解压/转换后占用明显放大 | OOM、磁盘低水位、任务超时 | 保持输入硬限，增加格式/页数/解压膨胀门和并发资源压力测；不以输入字节作唯一容量指标 |
| QyunsGen 自动消费不合格医学译文 | 受控临床字段出错或产生不可追溯的 AI 内容 | 只返回带来源和模型记录的译文草稿，强制临床业务确认，禁止默认自动回填 |
| 机器身份复用浏览器 CSRF / 用户 token | 被伪造调用、越权跨 tenant、凭证泄露 | 服务身份单独签发/校验，最小权限、短时令牌、审计、密钥轮换，不放前端 |
| DeepSeek 测试外发资料与本地 profile 的分级冲突 | 文件内容泄露 | 外部全文 profile 只对 `public` 开放；任何临床样本外发前确认分级、数据授权和脱敏 |

## 8. 当前结论与待确认项

- **按拟定的 2 个文档任务上限：当前空位 2/2。** 当前代码还没有全局上限，PLAN-081b 实施后才是强制上限。数据库可见的新任务执行数为 0；两条旧版 translating 状态是陈旧记录待核对。
- **本次没有验证模型端两路可用。** 最新 Qwen 直连请求超时；此前 Ollama 配置观测为 `NUM_PARALLEL=1`。故当前只能确认应用账面有 2 个候选任务槽，不能承诺两个任务都实时并行推理。
- **文件边界：** 默认硬限 256 MiB、分片 8 MiB；建议上线显式固定 256 MiB，并在真实双任务压力测后设软提示阈值。目前没有依据把它增大。
- **模型判断：** 本地 Qwen 是可在自有 GPU 部署的开放权重模型，当前证据证明它可作为内部翻译引擎候选，不证明它是专用翻译模型。DeepSeek 单样本更快且数字检查更高，但属于外部服务且本文档差异未做人审，不能以相似度或速度单独定优劣。
- **i18n 判断：** PLAN-516 有助于 locale、页面字典和双语字段显示；不替代翻译模型、模型 API 或临床译文审校。

仍需在 081a/081d 确认：Qwen 主机当前服务状态与显存余量；QyunsApps/Authentik 的服务身份可签发方式；QyunsGen 自动提交的业务触发事件与目标字段清单；临床审阅人及质量阈值。
